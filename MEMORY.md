### ENV-001 — Краш Forward+ (Vulkan) под RDP

**Симптом:** Godot 4.7.2 (.NET) падает при запуске редактора/игры с дефолтным рендером
Forward+ (Vulkan). В журнале Windows — `Application Error`, faulting module `nvcuda64.dll`
(драйвер NVIDIA), код `0xc0000005` (access violation). Остаются crash-дампы в
`%LOCALAPPDATA%\CrashDumps`.

**Диагностика (2026-10-09):**
- Рабочая сессия — **RDP**: `qwinsta` показывает `rdp-tcp#0`, активная сессия ID 1;
  локальная консоль (сессия 2) отключена. Используется виртуальный
  «Microsoft Remote Display Adapter».
- Стек краша: `vulkan-1.dll` → `nvoglv64.dll` (NVIDIA) → `graphics-hook64.dll` → `nvcuda64.dll` → 💥.
- Воспроизведение: Forward+ → краш (`-1073741819` = `0xC0000005`); **gl_compatibility
  (OpenGL→ANGLE→D3D11) → успех (exit 0)**; редактор с `--rendering-method gl_compatibility`
  стабильно живёт.
- Дополнительный фактор: в системе **глобально прописан хук OBS** как Vulkan-слой —
  `HKLM\SOFTWARE\Khronos\Vulkan\ImplicitLayers` → `C:\ProgramData\obs-studio-hook\obs-vulkan64.json`
  (layer `VK_LAYER_OBS_HOOK`, DLL `graphics-hook64.dll`). Грузится во все Vulkan-приложения
  даже без запущенного OBS. Присутствует в стеке краша.

**Первопричина:** комбинация *Vulkan-NVIDIA + RDP*. RDP подсовывает виртуальный дисплей, и
Vulkan-путь драйвера NVIDIA не работает; глобальный хук OBS усугубляет. **Логика игры ни при чём**
(ядро и тесты проходят, headless-запуск стабилен).

**Обход (применён):** запускать редактор/игру с `--rendering-method gl_compatibility`.
Скрипты: `tools/open-editor.cmd`, `tools/run-game.cmd` (см. `tools/README.md`).

**Варианты полного устранения (требуют прав администратора/настройки окружения):**
1. Убрать глобальный OBS-Vulkan-слой (`obs-vulkan64.json` из `ImplicitLayers`) или отключить
   Game Capture в OBS.
2. Обновить/переустановить драйвер NVIDIA.
3. Включить GPU-ускорение для RDP (Group Policy: «Use hardware graphics adapters for all
   Remote Desktop Services sessions»).
4. Не использовать GUI-редактор по RDP (разработка headless + локальный запуск редактора).

**Побочный симптом RDP:** WASAPI не инициализируется (нет аудиоустройства в сессии),
Godot падает на dummy-драйвер звука — не критично.

## 3. Принятые архитектурные решения (ADR-lite)

> Каждая запись: **Решение**, **Почему**, **Альтернативы**, **Последствия**.

### ADR-001: Godot 4.4+ (.NET) + C# 12 / .NET 8
- **Решение:** движок Godot 4.4+ с поддержкой .NET, основной язык C# (GDScript — только по необходимости).
- **Почему:** бесплатный движок с открытым кодом, первоклассная поддержка C#, быстрый прототипинг 3D и UI.
- **Альтернативы:** Unity (тяжелее, лицензирование), Unreal (оверкилл для скоуп-проекта), собственный движок (слишком долго).
- **Последствия:** зависим от версии .NET, поддерживаемой текущей сборкой Godot .NET.

### ADR-002: Разделение «чистое ядро» и «слой движка»
- **Решение:** вся игровая логика (генерация, экономика, алхимия, сохранения) живёт в чистом C# без зависимости от `Node`/`Vector3`.
- **Почему:** тестируемость без движка, детерминизм, переносимость, возможность headless-сервера.
- **Альтернативы:** писать всё сразу на `Node` (быстрее старт, но неподъёмное тестирование).
- **Последствия:** нужны DTO/мапперы на границе ядро↔движок; дисциплина обязательна.

### ADR-003: Детерминированный PRNG вместо `System.Random`
- **Решение:** собственный детерминированный генератор (`SplitMix64`/`Xoshiro`) для всех процедурных систем.
- **Почему:** воспроизводимость по сиду независимо от рантайма, .NET-версии и порядка вызовов; основа для мультиплеера и тестов.
- **Альтернативы:** `System.Random` (не гарантирует стабильность между версиями), `RandomNumberGenerator` (крипто, не нужен).
- **Последствия:** нужно самим реализовать и покрыть тестами; нельзя «дёшево» использовать `System.Random` в ленивых местах.

### ADR-004: 256 галактик с 8-битным индексом
- **Решение:** каждая галактика имеет уникальный 8-битный индекс (0–255), генерация — от (worldSeed, galaxyIndex).
- **Почему:** фиксированный масштаб вселенной, простые адреса/сохранения/синхронизация, галактика #256 (Odyalutai) как «пасхалка».
- **Последствия:** номер галактики — часть ключа генерации; миграция сидов должна это учитывать.

### ADR-005: Формат сохранений с обязательным `version`
- **Решение:** сохранения содержат поле `version`; сериализация — JSON (человекочитаемый) с возможностью бинарного режима.
- **Почему:** миграция старых сохранений, отладка, отказоустойчивость.
- **Последствия:** при каждом изменении схемы — миграция вверх + тест на совместимость.

### ADR-006: Детерминированная тик-симуляция и командная модель
- **Решение:** геймплейное состояние мира живёт в `WorldSimulation` (чистое ядро). UI/клиент **не мутируют** мир напрямую, а отправляют `IGameCommand` (Move/Jump/Buy/Sell/Chat). Мир применяет команды в порядке поступления, затем выполняет шаг физики на фиксированный `deltaSeconds`.
- **Почему:** (1) единый источник истины для одиночной игры и кооператива; (2) детерминизм — одинаковый сид + одинаковые команды дают одинаковый результат; (3) закладывает авторитарную серверную модель и, в перспективе, клиентское предсказание.
- **Альтернативы:** мутировать состояние прямо в сценах Godot (быстро, но несовместимо с нетворком и тяжело тестируется).
- **Последствия:** вся новая геймплейная логика должна проходить через команды; фиксированный шаг тика у всех участников.

### ADR-007: Абстракция транспорта и авторитарный сервер
- **Решение:** сеть строится на интерфейсе `IMessageTransport` и JSON-сообщениях (`NetworkMessage` + `CommandCodec`/`MessageCodec`). `GameServer` — авторитарен (проверяет `PlayerId`, применяет команды, рассылает снимки). В ядре есть `LoopbackTransport` для тестов и режима «одиночная игра = локальный хост». Реальный сокет-транспорт (ENet/WebSocket) подключается позже в слое движка.
- **Почему:** разработка и тестирование нетворка без сокетов; единый код для кооператива и сингла; позже меняется только реализация транспорта.
- **Альтернативы:** сразу привязаться к `ENetMultiplayerPeer` (быстрее, но непроверяемо в unit-тестах и связывает ядро с Godot).
- **Последствия:** сериализация через JSON (на Этапе 4 можно заменить на сжатый бинарный формат без смены архитектуры). Предсказание/лаг-компенсация — TODO.

### ADR-008: 3D-пространство системы и аркадная гравитация
- **Решение:** игровое пространство системы — трёхмерное (`Vector3D`). Корабль движется под действием тяги (по трём осям) и **сглаженной** гравитации звезды; планеты обращаются по кеплеровым орбитам, стыковка — в радиусе `DockRange`. Орбитальная модель (`StarSystemModel`, `OrbitalMechanics`) переиспользуется и симуляцией, и отрисовкой (единый источник данных).
- **Почему:** нужно для 3D-карты и полёта (SpaceEngine-стиль); сглаживание убирает сингулярность в ядре; общий модуль исключает рассинхрон вида и логики.
- **Грабли (зафиксировано тестом):** если орбитальная скорость внутренних планет превышает максимальную скорость корабля, стыковка физически невозможна. Поэтому гравитационный параметр орбит подобран ниже тяговых возможностей корабля.
- **Последствия:** столкновения, посадка на поверхность и топливная экономика полёта — TODO (TECH-004).
