# AGENT.md — Правила работы над проектом Dark Space

> Этот файл описывает, **как** harness/агент (и любой разработчик) должен работать над проектом.
> Если правило противоречит личному удобству — правило важнее. Если правило мешает — обсуди и обнови его здесь.

---

## 1. Роль и цель

Мы делаем **Dark Space** — процедурно генерируемый космический симулятор/RPG/выживание
на **Godot 4.7.2 stable (.NET)** и **C# 12 / .NET 8**.

Версия движка зафиксирована: не переходить на dev/beta/RC и не менять SDK без отдельного согласования.

Ключевые ценности проекта, в порядке приоритета:

1. **Работает** — код собирается, запускается, тесты проходят.
2. **Понятно** — следующий разработчик (или агент) разберётся без автора.
3. **Расширяемо** — процедурная генерация и мультиплеер закладываются с самого начала, а не «потом прикрутим».
4. **Атмосферно** — чёрный юмор, тёмная эстетика, дух Frontier: Elite II и 0x10c.

## 2. Стиль кода

### 2.1. Язык и платформа

- **C# 12**, целевая платформа **.NET 8** (`<TargetFramework>net8.0</TargetFramework>`).
- **Nullable reference types включены** для всего кода: `<Nullable>enable</Nullable>`.
- **ImplicitUsings включены**: `<ImplicitUsings>enable</ImplicitUsings>`.
- Предупреждения компилятора трактуются как ошибки там, где это разумно (`TreatWarningsAsErrors` для Core-логики).
- GDScript допускается **только** там, где C# объективно невозможен или крайне неудобен
  (например, часть шейдерных/анимационных утилит движка). Любой GDScript-файл обязан иметь комментарий,
  объясняющий, почему он не на C#.

### 2.2. Документация кода

- **XML-документация (`/// <summary>`) обязательна для всех `public` и `protected` членов.**
- Для сложной логики — короткие inline-комментарии, объясняющие **«почему»**, а не «что».
- Публичные методы процедурной генерации обязаны документировать:
  - какие параметры влияют на результат,
  - детерминированы ли они (от какого сида зависят),
  - какие исключения могут быть брошены.
- `// TODO: [ЛОР]` — маркер мест, где нужен лор/чёрный юмор (см. `SCENARIO.md`).
- `// TODO: [TECH]` — маркер технического долга. **Каждый такой маркер дублируется в `MEMORY.md` → «Известные проблемы».**

### 2.3. Форматирование

- Стандарт — **`.editorconfig`** в корне репозитория. Не спорь со стилем, а правь `.editorconfig`.
- Отступ — **4 пробела** (C#), **табуляция** в `.gd` по конвенции Godot не используется (используем 4 пробела).
- Длина строки — мягко до **120 символов**.
- Фигурные скобки — **на новой строке** (стиль Allman, как принято в .NET).
- Файл заканчивается одним переводом строки, без trailing whitespace.

### 2.4. Именование

| Сущность | Стиль | Пример |
|---|---|---|
| Класс / интерфейс / struct / enum | `PascalCase` | `GalaxyGenerator`, `IStarSystemProvider` |

- Namespace корня: `DarkSpace`. Далее по структуре папок (`DarkSpace.Core.Generation`, `DarkSpace.UI.Hud`).

## 3. Архитектурные принципы

- **SOLID** — каждая система отвечает за одно; зависимости — через интерфейсы, а не конкретные классы.
- **DRY** — общая логика в `src/Core/Utils` и `src/Core/Systems`, не копипастим между системами.
- **KISS** — простое решение лучше «архитектурного шедевра». Процедурная генерация не должна быть умнее, чем нужно для результата.
- **Разделение логики и представления (MVC/MVVM)**:
  - **Логика** (генерация, экономика, алхимия, сохранения) — чистый C# **без зависимости от `Node`**.
    Тестируется unit-тестами без запуска движка.
  - **Представление** (сцены, `Node`, рендер, UI) — тонкий слой, который **вызывает** логику и реагирует на её события.
  - **Запрещено** тащить Godot-типы (`Vector3`, `Node`, `Resource`) в ядро логики там, где нужна чистая тестируемость.
    Для границ используем DTO/POCO и явные мапперы.
- **Детерминизм** — любая процедурная генерация обязана быть воспроизводимой по сиду.
  Запрещено использовать `System.Random` напрямую — только внутренний детерминированный PRNG (`SplitMix64`/`Xoshiro`),
  чтобы результат не зависел от рантайма.
- **Асинхронность** — тяжёлые операции (генерация больших объёмов, загрузка/сохранение, сеть) не блокируют главный поток.

## 4. Запреты

> Нарушение пунктов из этого раздела — блокер на code review.

1. **Никаких хардкодных ассетов.** Все текстуры, звуки, модели, иконки, тексты генерируются процедурно
   или синтезируются из паттернов по сиду. Исключение — базовые UI-элементы и шрифты (см. `assets/`).
2. **Никаких `GD.Print` / `Console.WriteLine` в продакшн-коде.**
   Только `GD.PrintRich` (для форматированного вывода) или централизованный логгер (`ILogger` / `Logger`).
   `Console.WriteLine` допускается **только** в тестах и разовых утилитах.
3. **Никаких блокирующих вызовов в основном потоке.** `.Result`, `.Wait()`, `Thread.Sleep`,
   синхронное чтение больших файлов — запрещены в геймплейном коде.
4. **Никаких магических чисел** без именованной константы и комментария.
5. **Никакого мёртвого кода** в `main`. Не удалённое — помечай `// TODO: [TECH]` и заводи запись в `MEMORY.md`.
6. **Никаких секретов и личных путей** в репозитории (токены, `C:\Users\...` внутри кода).
7. **Никаких прямых мутаций состояния мира из UI.** UI шлёт команды/интенты, мир решает.
8. **Никакого `<Nullable>disable</Nullable>`** и глушения предупреждений через `#pragma warning disable` без причины в комментарии.

## 4.1. Физика прежде всего (physics-first)

> «Всё, что повторяет законы нашей вселенной, — идеальная копия; а значит, проверяемо математикой.»

Качество игровых систем проверяется **не по скриншотам, а по инвариантам и законам**, которые
должны сходиться численно. Это касается динамики корабля, орбит, экономики, алхимии — всего.

Правила:

- **Моделируем реальные законы.** Движение — второй закон Ньютона; гравитация — обратные квадраты
  (со сглаживанием лишь при необходимости избежать сингулярности); орбиты — Кеплер; топливо — ракетное
  уравнение Циолковского. Формулы живут в чистом ядре (`src/Core/Systems/Physics`) и переиспользуются.
- **Тесты проверяют законы, а не картинку.** Обязательны проверки: законы сохранения (энергия, угловой
  момент), vis-viva, третий закон Кеплера, достижимая Δv vs. ракетное уравнение, порог скорости убегания.
- **Одна физика — один источник истины.** Постоянные (μ звезды и т.п.) задаются в одном месте и
  используются везде (орбиты планет, гравитация корабля), чтобы «всё сходилось».
- **Численный интегратор устойчив.** Предпочтителен симплектический интегратор (полушаговый Эйлера),
  сохраняющий энергию орбиты на длинных интервалах; дрейф энергии ограничен и проверяется тестом.
- **Единицы согласованы.** Единицы длины/времени/массы самосогласованы; формулы размерно корректны
  (например, Δv = v_e·ln(m0/mf), mdot = F/v_e, скорость убегания = √2·круговая).
- **Допуски явны.** Тесты сравнивают с аналитикой с осознанным допуском (`precision`) и документируют,
  чем он обусловлен (ошибка интегрирования и т.п.).

## 5. Git и процесс

### 5.1. Ветки

- По решению DartPower в репозитории сохраняем **только `main`** (локально и на `origin`).
- Работаем небольшими логическими коммитами прямо в `main`; новые ветки/worktree без запроса не создаём.
- Перед коммитом проверяем сборку, тесты и `git diff --check`; не включаем чужие изменения.
- Удаляем старую ветку только после проверки, что её коммиты достижимы из `main`; без force-delete/reset.

### 5.2. Коммиты — Conventional Commits

```
<type>(<scope>): <краткое описание в императиве>

<тело: что и почему, а не как>

<footer: ссылки на issue, BREAKING CHANGE>
```

Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`, `build`, `ci`.
Скоуп — система: `generation`, `save`, `economy`, `alchemy`, `network`, `ui`.

Примеры:
- `feat(generation): add deterministic galaxy seed hashing`
- `fix(save): rotate backups keeping last 5 copies`
- `docs: initial project documentation`

### 5.3. Pull Request

- Текущий процесс — main-only; обязательные feature-ветки/PR отменены решением пользователя.
- В коммите/итоге фиксируем **что**, **зачем**, **как проверено**; GitHub Actions проверяет push в `main`.
- Если защита GitHub запрещает push, сообщаем блокер; не отключаем защиту и не используем force-push.
- Внешние PR допустимы по отдельному запросу; после слияния их локальные ветки не сохраняем.

### 5.4. .gitignore

- Godot: `.godot/`, `*.import` в части экспортов, `export_presets.cfg` (если содержит секреты), `.mono/`, `bin/`, `obj/`.
- IDE: `.vs/`, `.vscode/` (кроме общих настроек), `*.user`.
- ОС: `Thumbs.db`, `.DS_Store`.
- Артефакты сборки и экспорта в билд-папки.

## 6. Тестирование

- Фреймворк — **xUnit** (или NUnit, если появится веская причина; смена фиксируется в `MEMORY.md`).
- Тестовые проекты: `tests/UnitTests`, `tests/IntegrationTests`.
- **Unit-тесты обязательны для:**
  - процедурной генерации (галактики, системы, планеты, корабли, расы);
  - алхимии (комбинации элементов, именование ресурсов);
  - экономики (спрос/предложение, цены);
  - сохранений (сериализация, миграции, ротация бэкапов, восстановление повреждённых).
- **Интеграционные тесты** — для мультиплеера (P2P-хендшейк, синхронизация состояния, лаг-компенсация).
- **Свойства детерминизма** проверяются явно: `Generate(seed)` дважды → идентичный результат.
- Тесты — быстрые, независимые, без сети и без запуска движка (кроме интеграционных).
- Правило: **баг → сначала падающий тест, потом фикс.**

## 7. Производительность и многопоточность

- Тяжёлые вычисления — через `Task`/`Parallel` вне главного потока; результат отдаём в мир через очередь команд.
- Никаких аллокаций в горячих циклах без причины (переиспользуй буферы, избегай LINQ там, где это критично).
- Профилирование обязательно перед оптимизацией. Оптимизация без замера — не оптимизация.
- Сетевой код не блокирует игровой цикл; используем `ENetMultiplayerPeer`/`WebSocketMultiplayerPeer` и неблокирующие API.

## 9. Определение «Готово» (Definition of Done)

Задача считается выполненной, когда:

- [ ] Код собирается без предупреждений (`dotnet build`).
- [ ] Все тесты проходят (`dotnet test`).
- [ ] Добавлены/обновлены тесты на новую логику.
- [ ] Публичные члены задокументированы XML-документацией.
- [ ] `MEMORY.md` обновлён (changelog + при необходимости известные проблемы).
- [ ] Нет нарушений раздела «Запреты».
- [ ] Изменение оформлено отдельным логическим коммитом в `main`, проверки описаны.
